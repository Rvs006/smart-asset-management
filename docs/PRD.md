# PRD — Smart Asset Management Tool (SAM)

> Generated by ProductOS (Develop phase), August 2026. Source inputs: `docs/PRODUCT.md`, `docs/DESIGN.md`, `productos/design/2. Magic Moment.md`, `productos/design/3. Onboarding Flow.md`, and the Day 1 software specification (`docs/reference/day1-pack/Day1-Software-Specification.md`, ~95 SAM-* requirements). Stack decision: reuse the Smart Commissioning Tool's stack and GUI.

## 1. Overview

### Product Summary
SAM is a standalone, project-configurable web application that replaces the per-trade Excel "Smart Asset Registers" used on smart-building projects with one governed, validated database per project. Users define the naming convention and controlled reference lists once, import the project's own register schema, populate each trade's assets against validated dropdowns, and get continuous cell-level validation — including cross-trade duplicate detection — plus import/export back to spreadsheet at any time.

### Objective
Cut the multi-day manual consolidation and handover-rework each project currently burns, and make the consolidated register defensible (no cross-trade duplicates, no invalid references) by construction.

### Market Differentiation
Tuned specifically to MSI commissioning handover (importable per-project schema + cross-trade validation as the core, not an add-on), and delivered in the same UI and stack as the already-trusted Smart Commissioning Tool. No lock-in: full Excel import and export both ways.

### Magic Moment
Import a real CONTRACTOR ASSET sheet and instantly see the cross-trade duplicate Instance Names and invalid references Excel was hiding, traceable to the cell. Target: <60s from "Upload and validate" to the fault list; ≥80% of first real imports surface an agreed genuine fault.

### Success Criteria
- First real import surfaces at least one genuine fault the user agrees Excel would have missed (≥80% of imports).
- A project's consolidated register exports clean (zero unresolved cross-trade duplicates) on demand.
- Time to produce a consolidated register drops from days to minutes on a real project.

## 2. Technical Architecture

### Architecture Overview
React SPA (the SCT design language) ↔ FastAPI backend ↔ SQLite (local profile). Jobs (import/export/validation) run inline for the local profile; the design leaves room for a Postgres swap and background jobs later, exactly as SCT does. Dynamic project metadata is represented as **schema fields + per-asset JSON values**, never a physical table per project.

### Chosen Stack
- **Frontend:** React 19, Vite, react-router (hash router), TanStack Query, TypeScript — matching SCT. Styling: import SCT's `sct-styles.css` + `sct-electracom-theme.css` verbatim (copied into `frontend/src/styles/`), reuse the class names.
- **Backend:** Python 3.12, FastAPI, Uvicorn, `sqlite3` (stdlib) with parameterized queries, `openpyxl` for XLSX import/export, Pydantic for request/response models.
- **DB:** SQLite file under `%LOCALAPPDATA%\SmartAssetManagement` (mirrors SCT so data survives upgrades); a relational core plus JSON metadata column.
- **Packaging (later):** the SCT portable pattern (PyInstaller + bundled frontend `dist/`).

### Repository Structure
```
backend/   app/ (main.py, db.py, models.py, validation.py, naming.py, importer.py, exporter.py, seed.py, api/routes/*), tests/
frontend/  src/ (app/, features/{configuration,overview,assets}, api/, styles/), index.html, vite.config.ts
docs/      PRODUCT.md, DESIGN.md, PRD.md, ROADMAP.md, ...
```

### Infrastructure & Deployment
Local-first: binds 127.0.0.1, SQLite, jobs inline, no broker/Postgres/network required (SCT's "Developer/local profile"). Backend serves the built frontend from `/` and mounts `/assets`, so one process runs the whole app.

### Security Considerations
Local single-user loopback profile trusts 127.0.0.1 (as SCT does). No secrets in the client. Parameterized SQL only. File uploads (XLSX/CSV) validated and size-capped. Full detail belongs to the security audit (`docs/SECURITY-AUDIT.md`, step in the roadmap). Register data can contain IPs, MAC addresses, hostnames and a "Default Password" column — sensitive fields are masked in the UI and excluded from plain exports by default.

### Cost Estimate
Internal tool; cost is build + maintenance time. No per-seat SaaS or cloud spend in Day 1 scope.

## 3. Data Model

### Entity Definitions
- **Project** — `id, name, site_reference, building_reference, naming_scheme_id, name_mode ('auto'|'import'), active_schema_id, status ('active'|'archived'), created_at`.
- **Trade** — `id, project_id, code (BMS/EMS/…), name, system_owner, active`.
- **ReferenceValue** — `id, project_id, kind ('building'|'level'|'space'|'system'|'zone'|'equipment_type'), code, label, parent_ref (nullable), active`. (Controlled lists for dropdowns + validation.)
- **SchemaField** — `id, project_id, field_key, display_name, group, data_type, required ('yes'|'no'|'conditional'), conditional_expr (nullable), validation_type ('reference'|'unique'|'format'|'none'), reference_kind (nullable), unique_scope (nullable), auto_generated (bool), editable (bool), visible (bool), export_order`.
- **NamingScheme / NamingSegment** — scheme: `id, project_id, standard, mode, uniqueness_scope, case, site_ref_separate`; segment: `id, scheme_id, sequence, name, source_field, segment_type ('lookup'|'reference'|'fixed'|'number'), fixed_value, length, pad_char, pad_dir, delimiter_before, required, validation_rule`.
- **Asset** — `id (stable), project_id, trade_id, instance_name, metadata (JSON: field_key → value), created_at, updated_at, source ('manual'|'import'|'generated')`.
- **ValidationIssue** — `id, project_id, asset_id (nullable), field_key (nullable), severity ('error'|'warning'), rule, message, expected, resolved (bool), detected_at`.
- **ImportExportJob** — `id, project_id, kind, source_file, mode, counts (JSON), errors (JSON), created_at`.
- **AuditEvent** — `id, project_id, asset_id (nullable), user, action, before (JSON), after (JSON), at`.

### Relationships
Project 1—N Trade, ReferenceValue, SchemaField, Asset, ValidationIssue, Job, AuditEvent. Trade 1—N Asset. Asset 1—N ValidationIssue. NamingScheme 1—N NamingSegment.

### Indexes
`asset(project_id, instance_name)` (duplicate detection), `asset(project_id, trade_id)`, `reference_value(project_id, kind, code)`, `validation_issue(project_id, resolved)`, `schema_field(project_id, export_order)`.

## 4. API Specification

### API Design Philosophy
REST under `/api/v1`, JSON, project-scoped by `project_id`. Long operations return a job summary. Mirrors SCT's shapes where sensible.

### Endpoints (Day-1 / vertical-slice core marked ★)
- `GET /api/v1/health` ★
- `GET/POST /api/v1/projects`, `GET/PATCH /api/v1/projects/{id}` (create, list, select, archive) ★
- `POST /api/v1/projects/{id}/references/import` (XLSX/CSV), `GET /api/v1/projects/{id}/references?kind=` ★
- `GET/POST /api/v1/projects/{id}/trades` ★
- `POST /api/v1/projects/{id}/schema/import`, `GET /api/v1/projects/{id}/schema`, `GET /api/v1/projects/{id}/schema/template` (download) ★
- `POST /api/v1/projects/{id}/naming` (define scheme+segments), `POST /api/v1/projects/{id}/assets/generate-names` (auto mode)
- `POST /api/v1/projects/{id}/assets/import` (XLSX/CSV, modes: create / upsert-by-id) ★
- `GET /api/v1/projects/{id}/assets?trade=&search=` ★, `POST/PATCH/DELETE /api/v1/projects/{id}/assets[/{assetId}]` ★
- `POST /api/v1/projects/{id}/validate` (run full validation) ★, `GET /api/v1/projects/{id}/issues?trade=&severity=` ★
- `GET /api/v1/projects/{id}/overview` (metrics: counts, completeness, errors, duplicates per trade + cross-trade) ★
- `GET /api/v1/projects/{id}/export?trade=&format=csv|xlsx` (register), `GET /api/v1/projects/{id}/export/issues` ★(csv)
- `GET /api/v1/projects/{id}/audit`

## 5. User Stories

### Epic: Configure a project
- As a commissioning lead, I create a project and set its site/building reference and naming mode, so all downstream data is scoped and named consistently.
- As a lead, I import reference lists (levels, spaces, systems, zones, equipment types) so trades pick from validated dropdowns.
- As a lead, I import the project's CONTRACTOR ASSET template so the register has exactly this project's columns.

### Epic: Populate & validate (magic moment)
- As a trade engineer, I import my filled asset sheet and immediately see which cells are invalid and which Instance Names duplicate another trade's.
- As an engineer, I edit a flagged cell against a dropdown and watch the fault clear.
- As a lead, I open the fault list and jump straight to any offending asset/cell.

### Epic: Oversee & export
- As a lead, I see per-trade completeness, error counts and cross-trade duplicates on one overview.
- As a lead, I export a clean consolidated register (or a validation report) for handover.

### Epic: Name assets
- As an engineer on a greenfield-naming project, I auto-generate BDNS-aligned Instance Names from parameters.
- As an engineer on a BIM-named project, I import names and still have them checked for uniqueness/format.

## 6. Functional Requirements
(Condensed from the ~95 SAM-* requirements; IDs cross-reference the Day 1 spec.)
- **FR-Config (SAM-CFG-001..007):** create/select/archive projects; define naming standard + mode; manage trades; import/manage reference lists; import register schema; export project configuration.
- **FR-Naming (SAM-NAM-001..007):** auto-generate Instance Names from ordered segments (abbreviation, building, floor, zone, unique number) with padding/delimiters/uniqueness scope; import/manual names; reproduce the configured convention exactly; validate uniqueness + format on all names regardless of source.
- **FR-Schema (SAM-SCH-001..006):** import a project-specific schema; each field carries type, requirement, conditional expression, validation type, reference list, unique scope, auto/editable/visible flags, export order; changing the schema changes the register without code changes; generate a matching asset import template.
- **FR-Assets (SAM-AM-001..012):** view/filter/search/add/edit/delete assets per trade in a full-width grid; cell-level validation highlighting; selected-asset detail below the grid (Details/Validation/History); bulk edit/delete/generate-names.
- **FR-Overview (SAM-OV-001..009):** total assets, completeness %, assets-with-errors, cross-trade duplicates, naming compliance, missing mandatory, QR-required count, last-update, per-trade progress; cross-trade duplicate list.
- **FR-Validation (SAM-VAL-001..010):** invalid reference (level/space/system/zone/equipment-type not in lists); missing mandatory; conditional-required (e.g. QR Size required when QR Required = Yes); format (e.g. unique-local-number digit count, MAC/IP shape); **project-wide duplicate Instance Name across trades**; each issue traceable to project/asset/field with expected value.
- **FR-Import (SAM-IMP-001..005):** import references, schema, assets from XLSX/CSV; validate on import; reject invalid rows with field-level errors; asset import modes create vs upsert-by-stable-ID.
- **FR-Export (SAM-EXP-001..005):** export a trade or consolidated register and a validation-issues report to CSV/XLSX; sensitive fields excluded from plain export by default.
- **FR-Audit (SAM-AUD-001..005):** record create/import/edit events with who/when and before/after.

## 7. Non-Functional Requirements
- **Performance:** a register of ~5,000 assets renders and validates in the grid without freezing; validation run returns in a few seconds on the local profile; grid uses horizontal scroll + sticky headers, no page-level horizontal scroll.
- **Security:** parameterized SQL; no secrets client-side; uploads validated + size-capped; sensitive columns (passwords, keys) masked and export-excluded by default. Loopback trust in local profile only.
- **Accessibility:** status always text + colour; keyboard-navigable grid and forms; visible focus (accent ring).
- **Scalability:** schema-as-data + JSON metadata so any project shape works; Postgres-swap path preserved.
- **Reliability:** imports/exports are jobs with counts + errors; asset import is idempotent by stable ID; DB stored outside the app folder to survive upgrades.

## 8. UI/UX Requirements
All screens follow `docs/DESIGN.md` (import the two SCT CSS files; reuse class names). Shell: translucent header (ELECTRACOM mark, divider, "Smart Asset Management Tool" / "ASSET WORKSPACE", right-side pills incl. active-project + theme toggle), grouped stage tabs (Home | CONFIGURE: Configuration | REVIEW: Overview | MANAGE: Asset Management), 1180px column, card stack.

### Screen: Configuration
Hero card + Actions side card (Validate / Save / Export-Import config); collapsible sections with status chips — Project, Asset Naming Convention (standard + mode + live name preview + segment builder), Trades, Reference Lists (Register-Import panel per set + "n loaded" chip), Register Schema (import + "n parameters detected" + parameter list).

### Screen: Overview
KPI strip (Total assets, Completeness %, Assets-with-errors [danger], Cross-trade duplicates [danger]); second KPI row (naming compliant, missing mandatory, QR required, last update); per-trade progress run-cards (click → Asset Management for that trade); Data-quality-rules panel + Cross-trade duplicates panel; export buttons.

### Screen: Asset Management
Trade KPI row; toolbar (trade select, search, Filters, Columns, Import, Export, + Add Asset); full-width data grid with per-cell validation tint (red error / amber warning) and a per-row status token, checkbox column, Instance Name bold + muted description; selected-asset detail card below (Details/Validation/History toggles); "Faults & validation issues" list with "Open asset" links.

## 9. Auth Implementation
Local single-user loopback profile (SCT parity): backend trusts 127.0.0.1 and grants an admin-equivalent local principal; no login screen, no API key required in local mode. A hosted/multi-user profile (API keys, roles, project/site scopes) is a later phase modelled on SCT's `AUTH_MODE`/scopes — out of Day 1 scope.
